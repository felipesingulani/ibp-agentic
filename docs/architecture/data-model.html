0 · Resumo em 30 segundos

Um Postgres, vários clientes. Toda linha tem tenant_id e o próprio banco esconde as linhas dos outros clientes (RLS).
Cadastro (master data) — políticas, nós, capacidade, rotas, SKUs, contratos, vendas, drivers financeiros. Versionado: editar cria versão nova; nada é apagado.
Runtime — cenários, cartões de premissa, execuções do otimizador A4, decisões (aprovar/escalar), movimentos de execução (0014) e journeys D3 (0015). Export do plano aprovado (W7) = só leitura + audit, sem migration.
Novo cenário só destrava quando o cliente confirmou o cadastro (confirmed_at) e a prontidão do A4 não está block.

Fonte da verdade: contracts/v0-postgres-cadastro.sql (baseline “0001”) + db/migrations/0002…0018 + contratos W4–W7 + A1 CurvaDemanda (`a1.curva.v1`, sem DDL). 0018: sales_history CHECK period só YYYY-MM + CHECK qty >= 0 + UNIQUE (tenant_id, node_id, sku_id, period, source); reimport da mesma chave → API 409 (sem upsert V0); sem backfill; aplicada no Neon prod 31/10 17:09 America/Sao_Paulo (dpl_87QxbREJhZdskjfUoLSzZ3gSgwAm). Se esta página e o SQL divergirem, vale o SQL. Texto completo em DATA-MODEL.md.

2 · Cadastro (master data) e versionamento

Como funciona a versão (o ponto mais importante)

CampoSignificadoAnalogia
idId daquela versão (uma linha).“A edição 3 do documento.”
stable_id (0006)Id do objeto ao longo do tempo; todas as versões compartilham.“O documento, qualquer que seja a edição.”
version + is_currentNúmero da versão e se é a vigente. Banco garante no máximo 1 corrente por stable_id.“Edição vigente.”
  • Editar (PATCH, why obrigatório) = linha nova com o mesmo stable_id, version + 1; a anterior deixa de ser corrente.
  • Aposentar (DELETE, com why) = nenhuma versão fica corrente. Nada é apagado.
  • Referências usam stable_id, não o id da versão — renomear um nó não quebra capacidade, rotas nem vendas.
  • Referenciar algo aposentado ou o id de uma versão específica → 400 invalid_reference.
Tabelas de identidade (nodes_identity, skus_identity, 0006): uma linha por (tenant_id, stable_id), preenchidas por trigger quando nasce a 1ª versão. É contra elas que as FKs compostas apontam.
Agnóstico de indústria (0003/0005): tipos de nó, unidade, moeda e rótulos são configuração do tenant. Os nomes legados capacity_t_month/cost_per_ton ficam no SQL até a W0.2; a API já expõe capacity_per_period/cost_per_unit.

4 · Runtime: cenários, premissas, A4, decisões, execução e journey

scenarios — cenário versionado (code+version). leg: sales/supply/finance/composed · status: draft/ready/stale/archived. Criação pela API = Task 6 (grant na 0011; ver W2-WIZARD-API-CONTRACT.md).
premise_cards — type: NovaFilial · CurvaDemanda · Investimento · Gap. Gap precisa de nó (CHECK no banco); node_id = stable_id de nó corrente (0007). Gap aberto → prontidão warn. A1 CurvaDemanda: fields.schema=a1.curva.v1 · 18 pts mensais + anchor · série server-side a partir de sales_history (≥6 períodos) · sem migration (ver A1-CURVA-DEMANDA-CONTRACT.md).
a4_runs — banco: queued → running → feasible | partial | failed (+ discarded). API simplifica: done + outcome. Até 3 reasons (janela|capacidade|contrato|custo|outro) + counts_by_kind. Rodar com prontidão block → 409 a4_not_ready.
decision_events — approve | escalate com why obrigatório. API Task 7 / 0012: POST/GET append-only (SELECT+INSERT), FORCE RLS, FKs compostas. exportRef null V0 (W7 não preenche). Sem write-back.
execution_movements (W4 / 0014) — movimento programado/realizado por dia ligado a um run (mesmo cenário). kind: ship/receive/produce/transfer/other · status: posted → void (trigger; único UPDATE permitido) · sem DELETE. Exceção Pulse quando desvio > 15%.
journey_runs (W5 / 0015 · W6) — learning journey no tenant lab. status: open/conviction/landed/abandoned · steps forçados leverage → consensus → roles → conviction (409 steps_out_of_order) · land só admin|domain_owner via funções definer. Sem DELETE.
Export plano aprovado (W7, sem migration) — GET /api/plans/approved/export?format=json|csv: só basis=approved, papéis admin|domain_owner|finance, números = a4_runs.plan cru, 1 linha audit_log (export).

5 · O que significa “destravar Novo cenário”

Regra: tenant_settings.confirmed_at IS NOT NULL E prontidão do A4 state ≠ block.
Em português: o cliente disse “meu cadastro está pronto” e o cadastro tem o mínimo pro otimizador rodar.

Prontidão — GET /api/a4-readiness (só versões correntes)

ItemExigido quando“ok” se…
Políticasemprepolítica corrente de capital de giro, ou estoque + serviço — grupos de kind de tenant_settings.policy_kinds (F-1; {} → legado POLICY_KINDS)
Capacidadesemprealgum nó corrente com node_capacity corrente > 0 (não vem do campo do nó)
Rotasempreexiste rota corrente
Contrato de fornecedorsó com supply_external_in_scope = trueexiste contrato corrente (senão n/a)

block = falta item exigido · warn = ok, mas há nó sem capacidade, Gap aberto ou kind fora do vocabulário (policy_kind_unknown, W6 — nunca block) · ok = limpo.

  • confirmed_at não entra no state. A API devolve unlock.new_scenario = confirmado && state ≠ block para a UI (wire v0.3.2 da Didi).
  • Quem impõe no servidor é a Task 6 (criar cenário): 403 scenario_locked ou 409 a4_not_ready.
  • Limitação conhecida: confirmar não é desfeito automaticamente se o cadastro mudar depois.
